# Jev Decisions 0.6.0

This release adds the third way to answer a review. There are now three arrangements, and you pick one: Jev over a TypeSafe or OpenRouter key, Laya locally with no key, or Laya first with a hosted fallback. The last one is the new opt in chain, and it is the one place a review can leave your machine after a local attempt fails. Nothing about the four hosted modes or the plain local mode changed.

## Laya primary, hosted fallback, opt in by name

`JEV_PROVIDER_MODE` accepts four new values, named in the same style as the hosted chains:

| Mode | Providers tried, in order |
|---|---|
| `laya_then_typesafe` | `laya`, then `typesafe` |
| `laya_then_openrouter` | `laya`, then `openrouter` |
| `laya_then_typesafe_openrouter` | `laya`, `typesafe`, then `openrouter` |
| `laya_then_openrouter_typesafe` | `laya`, `openrouter`, then `typesafe` |

Laya answers first from the local server. A local attempt that fails falls through to the named hosted provider, and if that fails too, to the next one the mode names. The order is the literal reading of the mode name.

`validate_fallback_order` used to reject anything that was not hosted, and `laya` could not appear in a chain at all. It now accepts Laya as the first member of a chain, and still rejects it anywhere else. Three rules hold, and each one is a test:

- **Laya may lead a chain but never follow one.** `("laya", "openrouter")` is accepted; `("typesafe", "laya")` is rejected, because a local server replaces the hosted route rather than being tried after one of them.
- **A chain of `laya` alone is still not a fallback order.** The plain local mode is selected by its own name and builds exactly one provider, so nothing routes through a chain path to get to it.
- **No mode appends Laya.** Every mode that does not name it has a chain without it, asserted across all nine modes.

## A named hosted provider needs its key before the local review is sent

A `laya_then_*` mode is only safe to select when the hop it falls through to can authenticate. So a missing key for any named hosted provider fails at selection, before any hop runs, naming the environment variable:

```
JEV_PROVIDER_MODE=laya_then_typesafe needs TYPESAFE_API_KEY for its hosted fallback
JEV_PROVIDER_MODE=laya_then_typesafe_openrouter needs OPENROUTER_API_KEY for its hosted fallback
```

The alternative behavior, sending the case state to the local server and only then discovering that the fallback cannot authenticate, would waste the local review and report a failure for a mistake that was visible before the first request. A test holds this by handing in a transport that records every hop and asserting it was never called.

## The answer says which provider answered

A `laya_then_*` result carries a `provider_routing` block. Nothing else does, so the hosted modes and the plain local mode keep the exact response shape they returned before:

```json
{
  "provider_routing": {
    "provider": "typesafe",
    "provider_order": ["laya", "typesafe"],
    "fallback_used": true,
    "attempts": [{"provider": "laya", "error": "http://127.0.0.1:8123/v1/systemone connection refused"}]
  }
}
```

`provider` is the hop that answered, `provider_order` is the chain, `fallback_used` is true when the answering hop was a fallback, and `attempts` lists each earlier hop with its error. The block is surfaced by `jev_decide`, `jev_workflow`, `approval_review`'s result, and the `post_llm_call` record, so a fallback is visible wherever a review result is.

## The privacy consequence, stated plainly

In a `laya_then_*` mode a failed local attempt **sends the case state to the named hosted API**. That egress is the point of the mode, not a side effect of it, and it is why `laya` and `laya_then_*` are separate choices:

- Plain `laya` never leaves the machine. It has no hosted hop, so there is nothing to fall through to.
- A `laya_then_*` mode sends nothing to a hosted API while the local server answers, and everything it would have sent when the local server does not.

Choose `laya` when no egress is acceptable, and a `laya_then_*` mode when local first with a hosted backstop is worth that exposure. This is stated in the same place as the note that the plain local route never leaves the machine: the provider selection section of the README, `docs/reference.md`, `docs/approvals.md`, and `docs/integrations.md`.

The local hop is otherwise unchanged. A `laya_then_*` mode still sends no `Authorization` header to the local server, still requires `score` criteria as an ordered list of level descriptions, and still enforces that a returned score stays on the legend index scale `0..len(criteria)-1`. It keeps the 120 second local budget rather than the hosted 30 second default, because the local hop is the one that runs first on CPU.

## What could not be verified live

This machine has no hosted API key, so the hosted hop cannot be completed. Pointing the local hop at a dead port so it fails, then letting a chain continue, reaches both hosted endpoints and they refuse the synthetic key:

```
hosted fallback error: <urlopen error [Errno 111] Connection refused>; https://api.typesafe.ai/v1/systemone HTTP 401; https://openrouter.ai/api/alpha/decisions HTTP 401
```

That is a real refusal, not a 403 as an outage would look, because the endpoints answer and reject the credential. So the fallback is proven two ways: with injected synthetic transports that fail on the local URL and record the hosted attempt, and by a real chain that reaches the hosted endpoints and is refused for want of a key. No hosted review has ever succeeded on this machine, and none of the tests claim one did.
