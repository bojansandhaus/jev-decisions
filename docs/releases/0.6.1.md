# Jev Decisions 0.6.1

This release makes the local-first behaviour match the DOGA fork, and it brings the evidence needed to read it. Three changes: a consecutive failure breaker that bounds how often a broken local server can turn reviews into remote traffic, an audit of every log call on the decision path so no log line can carry the reviewed command, and two DOGA selector aliases for the arrangements this repository already had. Nothing about the four hosted modes or the plain local mode changed, and no default moved.

The headline quality evidence for this route is now DOGA's 100-question benchmark, summarised under [Evaluation and limitations](#evaluation-and-limitations). The short version: on the authored labels the local classifier agreed far less often than the hosted one, and the breaker cannot fix that.

## Added

### The consecutive failure breaker

A local failure may reach a hosted provider only three times in a row. `jev_client` now holds a counter and a lock with a hardcoded limit of three (`LOCAL_FALLBACK_FAILURE_LIMIT`): each local failure in a `laya_then_*` mode increments the counter, the first three are allowed to fall through to the named hosted provider, and the fourth and every one after it **re-raises the local error with no hosted request at all**. Any local answer that passes validation resets the counter to zero, on both the plain local path and the chain path, so a server that recovers is trusted again immediately.

The count is process state. It resets on restart, nothing is written to disk, and it is never shared between processes. That is deliberate: the point is to bound one running process's remote egress, not to remember a fault across a restart.

Because the counter counts **local** failures, it bounds remote egress identically in all four `laya_then_*` modes regardless of which hosted provider a mode names. A parametrised test drives `laya_then_typesafe`, `laya_then_openrouter`, `laya_then_typesafe_openrouter`, and `laya_then_openrouter_typesafe` through three fallbacks and a suppression, and asserts that the suppressed attempt calls the local server and nothing else. A suppressed fallback is reported at warning level before the local error is re-raised.

The plain `laya` mode has no hosted hop, so a local failure there neither increments the counter nor is suppressed. There is nothing to suppress, and the code mirrors that rather than inventing a state that never changes a route.

### Two DOGA selector aliases

DOGA names three arrangements `jev_api`, `laya_local`, and `laya_with_jev_fallback`. Two of those names did not exist here, so `JEV_PROVIDER_MODE` now accepts them and resolves them to a canonical mode before anything routes:

| DOGA name | Resolves to | Providers tried, in order |
|---|---|---|
| `laya_local` | `laya` | `laya` |
| `laya_with_jev_fallback` | `laya_then_openrouter_typesafe` | `laya`, `openrouter`, then `typesafe` |

The mapping is a table in `jev_client.MODE_ALIASES` and it is the whole mapping. Nothing is inferred from an alias name at request time, and the chain behind `laya_with_jev_fallback` is spelled out rather than implied: it names **both** hosted providers, OpenRouter first and direct TypeSafe second, which is the order DOGA's own Jev route uses and the order this repository's `openrouter` default provider sits in. Naming both providers also means the alias is not weaker than DOGA's fallback, which can reach either one. A `laya_with_jev_fallback` selection therefore requires both `OPENROUTER_API_KEY` and `TYPESAFE_API_KEY`.

`jev_api` is not an accepted value, because the hosted arrangement it names already has four explicit mode names here. To match DOGA's Jev route exactly, including its OpenRouter-first order, set `JEV_PROVIDER_MODE=openrouter_then_typesafe`. That is documented in [the reference](../reference.md#doga-selector-aliases) rather than left to inference.

Everything else is unchanged and still accepted. All nine canonical modes resolve exactly as before, asserted for every one of them, and an alias behaves identically to the mode it names: same provider order, same required keys, same `provider_routing` block, same error text. A parametrised test compares an alias and its canonical mode on a healthy local answer, on a local failure that falls through, and on a local failure in the plain local mode, and asserts the two outcomes are equal. An unaccepted value is rejected with an error listing all eleven accepted values, checked for five near-miss spellings.

## Changed

### Log hygiene on the decision path

The task was an audit, not a rewrite: confirm that no log call on the decision path can carry the reviewed command, the case state, or an answer, and fix any that can. This repository handles untrusted shell commands, so a command reaching a log stream is a real leak.

The audit found exactly one offender, in the companion approval provider:

- `integrations/approval-provider/__init__.py`, in `JevClient._create_chat_completion`: the per-decision `logger.info` ended with `for %r` and `safe_command[:60]`. That is the reviewed command in the log stream, redacted and truncated but still command text. **Fixed.** The line now reports the decision, its measured numbers, and the command length plus a truncation marker, so a row can be correlated with the `0600` JSONL decision record that already stores it by design.

The other four log calls in that file were audited and left alone:

- the `logger.debug` when the JSONL record cannot be written carries an `OSError` (a filesystem path), not case content;
- the `logger.debug` when the model list is unavailable carries the route's own URL and an HTTP error, not case content;
- the `logger.info` and `logger.warning` around provider registration carry the provider name and a registration error, not case content.

`jev_client.py` had no logging at all before this release. The two warnings added for the breaker log **only the exception class name** (`JevClientError`), plus the provider name and the limit, never the exception message and never the state. A test drives four failing reviews of a synthetic `aws s3 rm s3://private-bucket --recursive` state and asserts the captured log contains `JevClientError` and `suppressed` while containing neither the command nor the exception message. The exception message is not logged even though it is safe today, because the guarantee should not depend on a future message being safe.

The `provider_routing` block still reports the failing hop's error string in the *result*. That is the response, not a log line, and it is what tells a caller which hop failed.

### Documentation and version

`README.md`, `docs/reference.md`, `docs/integrations.md`, `docs/approvals.md`, and `.env.example` now describe the aliases, the mapping table, and the breaker, including the plain local case where there is nothing to suppress. `docs/reference.md` gains two sections: [DOGA selector aliases](../reference.md#doga-selector-aliases) and [the consecutive failure breaker](../reference.md#the-consecutive-failure-breaker). No documentation claims a hosted review has ever succeeded on this machine. `plugin.yaml` and `pyproject.toml` both read 0.6.1.

## Evaluation and limitations

### The quality evidence is DOGA's 100-question benchmark

This repository did not re-run the benchmark, and it does not claim a local quality result of its own. The evidence for how good the local route is comes from DOGA's paired 100-question evaluation, replayed through a registered hook in a fresh process across 15 topics, with 100 prompts and 300 hook evaluations (one per setting, not 300 questions):

| Measure | Laya local | Jev API | Laya with fallback |
| :--- | ---: | ---: | ---: |
| Goal label agreement | 56/100 | 88/100 | 56/100 |
| Mode label agreement | 41/100 | 68/100 | 41/100 |
| Stakes label agreement | 37/100 | 67/100 | 37/100 |
| Scenario label agreement | 59/100 | 70/100 | 59/100 |
| High versus low ambiguity agreement at 0.7 | 67/100 | 87/100 | 67/100 |
| Authored high-ambiguity cases detected | 0/30 | 21/30 | 0/30 |
| Provider HTTP attempts | 0 | 100 OpenRouter, all 200 | 0 |

Read that table as what it is. Goal 56 against 88, mode 41 against 68, stakes 37 against 67, ambiguity 67 against 87. The local route detected **none** of the 30 authored high-ambiguity labels at the existing 0.7 threshold, so a focused-question contract that the hosted route produced was simply absent from the local one on those cases. The labels were authored before the local comparison and are subjective, not an independently adjudicated ground truth, and no final answers were scored. It is evidence about a classifier, not about answer quality, and the honest reading is to keep the hosted route as the recommended default while this checkpoint is uncalibrated.

The benchmark also measured the arrangement this release adds. Laya with the fallback enabled was **identical** to local-only across all 100 cases: 56, 41, 37, and 67, and zero provider HTTP attempts. That is the same property the tests here pin, arrived at independently: the fallback is reached only on a local exception, so a healthy local server means no hosted traffic at all, and the fail-through arrangement is not a second or better classifier.

### What the breaker does and does not do

The breaker bounds repeated remote egress after local **errors**. It **cannot detect a valid yet incorrect local judgment**. A confidently wrong local answer passes validation, is returned as a healthy local answer, and never reaches the hosted hop. Given the benchmark rows above, that is the limit that matters most, and it is why the breaker is described as an egress control rather than a quality control. The checkpoint's confidence is also uncalibrated: its saved choice temperatures trigger an upstream warning and are clamped, so no threshold here was tuned on the benchmark set.

The count is also per process by design. A process that restarts gets a clean counter, which is correct for bounding one process's traffic and wrong if what you wanted was a persistent failure memory. Nothing is persisted.

### The hosted leg is unit tested only

This machine has no hosted API key. The hosted hop of the aliases and of every `laya_then_*` mode is proved with injected synthetic transports that fail on the local URL and record the hosted attempt, plus selection-time assertions that a missing named key raises before any hop runs. A live call against a real hosted endpoint was not made, and no test claims one succeeded. The live tests call the real local `laya-serve` and assert that no fallback happened, which is also the evidence that nothing was sent to a hosted API.
