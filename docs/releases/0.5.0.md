# Jev Decisions 0.5.0

This release adds the other way to answer a review. There are now two arrangements, and you pick one: Jev over a TypeSafe or OpenRouter key, or Laya locally with no key. Nothing about the four hosted modes changed.

## One arrangement or the other, never a chain

`JEV_PROVIDER_MODE` accepts `laya` alongside `typesafe`, `openrouter`, `typesafe_then_openrouter`, and `openrouter_then_typesafe`. The local mode points the same review at a `laya-serve` process on your own machine.

Laya is not a hosted Jev endpoint and it is not a third route in a fallback chain. It is a separate model that answers the same `POST /v1/systemone` contract, so selecting it replaces the hosted pair instead of extending it. Three rules follow, and each one is a test:

- `laya` is exactly one provider. There is no second hop, because there is no second credential to find.
- No hosted mode selects the local route on its own. A pinned `typesafe` or `openrouter` mode never reaches loopback, and the two chained modes are still the hosted pair in either order.
- An order containing `laya` is rejected as a fallback member. A local route that replaced the hosted providers cannot also be tried after one of them fails.

The local route needs no key. `LAYA_API_KEY` is forwarded only when your server was started with its own bearer check, and when there is no key the `Authorization` header is omitted entirely rather than sent as an empty bearer. A test captures the outgoing headers and asserts that an unconfigured local request carries `Content-Type` and nothing else.

Point it at your server with `JEV_LAYA_BASE_URL` (default `http://127.0.0.1:8123`), `JEV_LAYA_ENDPOINT_PATH` (default `/v1/systemone`), and `JEV_LAYA_MODEL` (default `english`). Plain HTTP is accepted on loopback only, because a keyless request to another host would put the reviewed state on the wire unauthenticated and unencrypted.

## A local score question has to send ordered levels

This repository asks all three question types, not just `noul`: a `verdict` choice, a `blast_radius` score, and several `noul` questions. The local server answers all of them, but it is stricter about one shape. A `score` question must send `criteria` as an ordered list of level descriptions, index 0 first. A dict has no order to index and the server refuses it out loud with a `ValueError` naming the question id, so the plugin rejects that shape before the request instead of turning it into a failure at the server. `choice` keeps dict criteria of option to description, and the answer's `choice` is the winning label.

## The score scale was measured, not assumed

The `blast_radius` hardening thresholds in `approval_policy` (1.6 and 2.0) are only meaningful if the score they are compared against is on the scale they were written for. So both routes were asked the same three level question (`["trivial", "annoying", "severe"]`) about the same command state on 2026-09-26:

- Hosted, through OpenRouter: `score 0.72`, `probabilities {0: 0.42, 1: 0.44, 2: 0.14}`.
- Local, through `laya-serve`: `score 1.2068`, `probabilities {0: 0.1079, 1: 0.5773, 2: 0.3148}`.

Both numbers are the expected level on the legend index scale, `0..N-1`, and each one is exactly the expectation of its own distribution. So the local scale matches the scale the thresholds were written against, and the thresholds are unchanged. They are not portable to a question with a different number of levels, which is why the local route now asserts that a returned score stays inside `0..len(criteria)-1` and that the returned legend matches the levels it was asked about. A score outside that range is an error rather than a number to compare.

## What the local route is not

The base English checkpoint is a small model on CPU, and three measured limits say plainly what it is worth:

- **Slow.** CPU inference measured roughly 1.6 seconds per question row, and a six question review took about 2 seconds once loaded. Model load takes 25 to 35 seconds, and one process answers one forward pass at a time. The local route therefore gets a 120 second budget rather than the hosted 30 second default.
- **Weakly separated, so the policy escalates.** A live local `verdict` answer returned `confidence 0.1119` against the `0.55` floor in `approval_policy`, and the end to end local approval review returned `ESCALATE` on `self_advocating 0.83 >= 0.6` instead of approving. That is the policy behaving as designed on a spread out answer, but it means switching to the local route changes decisions, not just where they are computed.
- **No quality claim.** On the compaction retention evaluation in the companion plugin, this base checkpoint's zero shot discrimination between keep and drop was near zero: a 0.0014 gap between the classes, with calibration hitting its 0.40 ceiling. Those figures were measured there, not here, and they are reported here only to bound what a local score is worth. Calibrate on your own labelled examples before trusting the local route for a consequential decision.

Laya is not vendored, copied, or adapted in this repository, and it is not a dependency of the package. The route speaks the wire contract Laya publishes and nothing else. `THIRD_PARTY_NOTICES.md` records the attribution: `laya` 0.3.20, `Author: Convai Innovations`, `License: Apache-2.0`, and `laya/serve.py` describing itself as an "HTTP server exposing Laya over TypeSafe Jev's ``/v1/systemone`` wire protocol".
